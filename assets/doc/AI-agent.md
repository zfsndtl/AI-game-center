# AI Agent 核心技术概念全景文档

## 1. ReAct：AI 智能体的“思考-行动”范式

### 1.1 什么是 ReAct？

ReAct（Reasoning + Acting 的缩写）是由**谷歌研究院和普林斯顿大学于 2022 年**联合提出的一种大语言模型（LLM）提示范式。其核心思想是让模型通过交替进行**推理（Reasoning）**和**行动（Acting）**来解决复杂任务，而非一次性生成最终答案。

### 1.2 诞生背景

在 ReAct 提出之前，LLM 解决复杂问题主要依赖两种路径，但各自存在严重缺陷：

| 已有方法                            | 核心机制                                             | 核心缺陷                                                     |
| :---------------------------------- | :--------------------------------------------------- | :----------------------------------------------------------- |
| **思维链（Chain-of-Thought, CoT）** | 模型通过逐步推理来解决复杂问题。                     | 在“信息真空”中进行，完全依赖模型内部静态知识，容易出现事实错误和“幻觉”，且无法获取实时信息或更新知识库。 |
| **仅行动规划（Act-Only）**          | 模型生成一系列操作与外部环境互动（如在文本游戏中）。 | 缺乏明确的高层规划和推理能力，遇到意外情况时无法灵活调整策略。 |

**ReAct 的提出正是为了协同这两者的优势**：让模型既能像 CoT 一样进行清晰的推理，又能像 Act-Only 一样与外部世界交互，从而将推理“锚定”在真实的外部反馈上。

### 1.3 核心机制：TAO 闭环

ReAct 的工作流程是一个 **“思考-行动-观察”（Thought-Action-Observation, TAO）** 的迭代循环：

- **Thought（推理）**：模型分析当前任务状态，明确“下一步该做什么”及其依据。这一步让决策过程透明、可追溯。
- **Action（行动）**：模型执行一个外部操作，如调用搜索引擎、API 或数据库查询，将推理转化为实际行动。
- **Observation（观察）**：外部工具返回执行结果，模型将其作为新的上下文，形成反馈闭环，修正后续推理。

**示例流程**（事实核查任务）：

text

```
用户问：交流电的发明者出生于哪个首都城市？

Thought 1：我需要查明交流电的发明者，再找到他的出生地。
Action 1：Search[交流电发明者]
Observation 1：交流电由尼古拉·特斯拉开发和推广。

Thought 2：现在需要找出特斯拉的出生地。
Action 2：Search[特斯拉出生地]
Observation 2：特斯拉出生于斯米连村（现属克罗地亚）。

Thought 3：斯米连不是首都。基于出生地事实回答。
Final Answer：特斯拉出生于斯米连，该地不是首都。
```



### 1.4 ReAct 与 Function Calling 的区别

在构建 AI Agent 时，ReAct 和 Function Calling 是两种最常见的策略，它们在**工作模式、适用场景、效率**上有显著差异。

| 对比维度       | **Function Calling**                       | **ReAct**                                                |
| :------------- | :----------------------------------------- | :------------------------------------------------------- |
| **工作模式**   | 单轮“意图→工具映射”                        | 多轮“思考→行动→观察→再思考”循环                          |
| **核心逻辑**   | 精准调用预定义工具                         | 动态推理，根据反馈调整策略                               |
| **效率与成本** | 高（一次调用，tokens 消耗少）              | 低（多次 LLM 调用，tokens 消耗大）                       |
| **适用复杂度** | 简单、明确的任务（如数据库查询、API 调用） | 复杂、多步骤、路径不明确的任务（如旅行规划、开放式研究） |
| **可解释性**   | 较低（仅输出工具调用结果）                 | 较高（推理过程透明可见）                                 |
| **稳定性**     | 高（依赖工具注册清晰度）                   | 依赖 LLM 推理能力与提示词质量                            |

**在实际开发中，这两种策略可以组合使用**：简单查询走高效的 Function Calling 通道，复杂任务则交给 ReAct 引擎进行迭代推理。

## 2. Harness：AI 智能体的“操作系统”

### 2.1 什么是 Harness？

在 AI 工程领域，**Harness** 指的是**包裹在模型外部的完整工程基础设施**，用于将无状态的 LLM 转化为稳定、可控、可投入生产的智能体系统。

如果说 ReAct 是“教模型如何思考-行动的思维模式”，那么 Harness 就是“给模型配齐工位、权限卡、公司制度和协作流程”。

### 2.2 Harness vs. ReAct：核心区别

| 维度           | **ReAct**                                    | **Harness**                                                  |
| :------------- | :------------------------------------------- | :----------------------------------------------------------- |
| **是什么**     | 提示/执行模式（Prompt Pattern）              | 一套完整的工程基础设施                                       |
| **层级**       | 模型内部认知层                               | 模型外部工程层                                               |
| **解决的问题** | 模型不会主动查资料、调工具、做多步推理       | 模型能干活但不可控：权限怎么管？记忆怎么存？上下文溢出怎么办？多任务怎么协作？ |
| **包含内容**   | Thought → Action → Observation 循环          | 对话循环 + 工具调度 + 权限管线 + 上下文管理 + 记忆系统 + 子Agent编排 |
| **类比**       | 教人“遇到问题先想、再做、再看结果”的思维习惯 | 给这个人工位、工具、权限卡、公司制度和验收标准               |

### 2.3 Harness 的六大核心子系统

根据对 Claude Code 等生产级 Harness 的拆解，一个完整的 Harness 通常包含以下子系统：

1. **对话循环（心脏）**：最简的 while(true) 循环，所有智能推理交给模型，但循环本身提供框架支撑。
2. **工具调度（手脚）**：管理模型可调用的所有外部工具（搜索、API、数据库等），支持并发和读写分离。
3. **权限管线（刹车）**：多层防御机制，防止模型执行危险操作（如 `rm -rf /`）。
4. **上下文管理（记忆）**：自动压缩历史记录、分层加载、熔断保护，解决上下文溢出问题。
5. **子Agent编排（协作）**：管理多个 Agent 之间的分工与通信，通过“上下文防火墙”实现隔离。
6. **MCP 协议（接口）**：标准化 Agent 与外部工具的通信协议。

### 2.4 生产级 Harness 实践

以 Harness 平台自身的 AI 能力为例，其 AI 功能涵盖多个模块：

| 模块               | 功能描述                                                     |
| :----------------- | :----------------------------------------------------------- |
| **Harness Agents** | 自主 AI Agent，可在 pipeline 内部执行构建、部署、测试、修复等任务 |
| **DevOps Agent**   | 用自然语言创建 pipeline、分析构建/部署失败根因               |
| **Worker Agents**  | 在 pipeline 步骤内运行的自主 AI，用于代码审查、事件响应等    |
| **AI Rules**       | 将企业标准注入 AI 输出，确保符合规范                         |
| **MCP Server**     | 通过标准化协议让 AI Agent 完整访问 Harness 平台              |

### 2.5 Big Model vs. Big Harness 的行业争论

AI 工程圈对“模型能力更重要还是框架更重要”存在争论：

- **Big Model 派**：认为随着推理模型能力提升，复杂的框架脚手架终将被淘汰。Claude Code 创始人直言“秘诀都在模型里，框架只是最薄那层包装”。
- **Big Harness 派**：认为 Harness 就是产品本身。有实践表明，仅通过规范化 `CLAUDE.md` 文件，同一模型的任务完成率从 52.8% 提升至 66.5%。

**两派共识是：好马配好鞍，模型和 Harness 的协同优化才能跑得更远。**

## 3. Agent 设计模式全景

### 3.1 主流 Agent 设计模式概览

AI Agent 的设计模式可归纳为以下三大路线：

| 路线                          | 代表             | 核心特征                                                     | 适用场景                                           |
| :---------------------------- | :--------------- | :----------------------------------------------------------- | :------------------------------------------------- |
| **流程智能化 (Workflow)**     | Coze             | 通过预先定义的流程图（DAG）驱动 LLM，流程确定可控            | 客服工单处理、ETL 数据管道等需要高稳定性的业务场景 |
| **智能体智能化 (Autonomous)** | DeerFlow         | 单个 Agent 具备自主认知和决策能力，自行规划、探索、反思      | 撰写研究报告、创新策划等充满不确定性的开放性问题   |
| **混合智能架构 (Hybrid)**     | 当前业界主流趋势 | 在规划阶段生成包含分支与合流的动态执行图，兼具稳定性与灵活性 | 大多数真实生产环境                                 |

### 3.2 ReAct Agent vs. CodeAct Agent

ReAct 和 CodeAct 是两种代表不同技术路线的 Agent 架构，其最核心的区别在于 **“行动（Act）”的实现方式**。

| 对比维度         | **ReAct Agent**                   | **CodeAct Agent**                                    |
| :--------------- | :-------------------------------- | :--------------------------------------------------- |
| **行动方式**     | 生成结构化指令（JSON）调用工具    | **直接生成可执行代码**（Python）                     |
| **逻辑处理能力** | 较弱，指令链难以处理复杂分支      | **极强**，天生支持 if/else、循环等逻辑               |
| **可解释性**     | **高**，推理过程完全可见          | 中，需理解生成代码的逻辑                             |
| **适用场景**     | 5-10 步以内的线性任务，如简单问答 | **复杂、多步骤、强逻辑**的任务，如数据分析、金融风控 |
| **主要挑战**     | 上下文膨胀与长链路错误累积        | **代码安全与执行环境的隔离**                         |

**典型应用案例**：

- 某电商平台的智能客服通过 ReAct 架构，实现了 20 多种业务流程的自动化，准确率达到 92%。
- 一个金融风控系统用 CodeAct 架构，将原本需要 12 个 JSON 配置文件实现的规则引擎，简化为 3 个核心代码模板，效率提升 4 倍。

## 4. 三者对比总结

| 维度         | **ReAct**                    | **Harness**                      | **CodeAct**                    |
| :----------- | :--------------------------- | :------------------------------- | :----------------------------- |
| **核心定位** | LLM 推理-行动范式            | AI 智能体工程基础设施            | Agent 的代码化行动模式         |
| **解决问题** | 让模型主动调用工具、多步推理 | 让模型从“能聊天”变成“能稳定干活” | 让模型通过生成代码处理复杂逻辑 |
| **适用层级** | 模型认知层                   | 系统工程层                       | 模型行动层                     |
| **类比**     | 人的“思考-行动”思维习惯      | 公司的管理制度和基础设施         | 把“说话”变成“写代码”的工作方式 |

这三者构成了 AI 从**认知能力**（ReAct）到**行动能力**（CodeAct）再到**工程化**（Harness）的完整技术链条。
